## AI 编程规范

### 禁止不经思考完全依靠 AI 开发

- 直接向 AI 下达笼统指令，例如「帮我开发 xxx 功能并提 PR」「帮我修这个 bug 并提 PR」。
- 用 AI 生成大量难以维护、难以理解的「黑盒」代码——例如毫无意义的过度封装，或为简单功能堆砌代码。
- 提交自己看不懂、无法掌控的代码。

> [!CAUTION]
> 禁止在未向 AI 提供游戏界面截图、界面跳转逻辑等上下文的情况下，让 AI 直接编写。
> 
> MaaFramework 的 Pipeline 强依赖游戏界面与业务逻辑，缺乏界面信息的 AI 只能依赖幻觉和项目已有代码拼凑，产出代码质量极低。
> 充分的信息至少包括：每个识别节点需提供 roi 与模板图片，并说明界面间的跳转关系（从哪个界面、点击什么、跳转到何处）。
> 
>Custom 代码通常只由作者本人维护。若连作者都看不懂，其他人更不敢动。不能不经思考，让 AI 全权负责修复，自己既不 review，也不理解改动。
> 
> 不满足以上条件的 PR 将被直接关闭。

### 推荐的 AI 开发方式

- 先了解项目结构和编码规范，
- 仅将 AI 的建议作为参考。
- 用 AI 做有目标的增量开发，自行 review 是否符合预期。
- 测试无误后再提交 PR。

### 先复用，再新增

写新代码前，先查现有代码（不要遗漏 `utils.json`），确认是否已有现成能力。

## ROI 与分辨率

- 截图按**短边 720** 归一化（MaaFramework 自动缩放）
- 所有 Pipeline ROI 基于短边 720 基准编写
- ROI 应精确限定在目标元素可能出现的区域内，不要全屏识别，这既浪费性能又容易误判。

> 小技巧：先大范围识别测试一次，在测试结果中复制对应节点的 "best" 结果作为识别范围，然后测试第二次。如果第二次测试有问题，可以将范围扩大几像素作为容错。

## Git 提交规范

Commit Message 格式：

```
<type>: <简短描述>
```

常用提交类型：

| type | 说明 | 示例 |
| --- | --- | --- |
| `feat` | 新功能 | `feat: 添加每日和每周周期任务控制` |
| `fix` | Bug 修复 | `fix: 修复复盘确认弹窗的交互逻辑` |
| `refactor` | 代码重构 | `refactor: 移除未使用的文件` |
| `chore` | 杂项维护 | `chore: 更新JSON Schema` |
| `ci` | CI/CD 变更 | `ci: 更新 MaaFw 版本至 v5.12.2` |
| `docs` | 文档更新 | `docs: 更新思绪残影章节信息` |
| `style` | 格式调整 | `style: 更新 logo 文件，统一颜色感知亮度` |
| `revert` | 回滚 | `Revert "refactor: 移除未使用的文件"` |

## PR 规范

提交 PR 时，请遵守以下规则：

- **范围单一**：一个 PR 只解决一个明确问题，避免混入无关格式化、重构或功能改动。
- **说明完整**：PR 描述应写清楚改动原因、影响范围和验证方式。
- **功能描述**：描述功能作用。
- **验证**：执行了什么验证、结果如何（不要只写"已测试"）。

可以使用 AI 辅助，但提交者必须理解并能解释 PR 中的关键改动。

> 不要提交本地缓存、运行产物、调试截图或下载得到的模型文件。

## Pipeline JSON 编写规范

### 2.1 文件组织

- Base 目录：`assets/resource/base/pipeline/` 存放所有服务器共用的 Pipeline。
- 渠道覆盖：`assets/resource/bilibili/pipeline/` 和 `assets/resource/intl/pipeline/` 仅存放与 base 不同的节点（如 startup、shutdown），程序会先加载 base 再加载渠道目录，同名字段将被覆盖。
- 任务入口：`assets/resource/tasks/T_*.json` 存放任务配置（含用户可配置选项）。
- 一个 JSON 文件对应一个游戏功能模块。

### 2.2 节点命名规范

这是 MaaTOT 项目约定，MaaFramework 上游无此规定。

| 前缀 | 类型 | 说明 | 示例 |
| --- | --- | --- | --- |
| `Click_` | 动作节点 | 执行点击操作 | `Click_返回主界面键`、`Click_邮件` |
| `Swipe_` | 动作节点 | 执行滑动操作 | `Swipe_向上滑动寻找进修副本` |
| `Flag_` | 纯识别节点 | 判断当前画面状态，不执行动作 | `Flag_主界面任务`、`Flag_复盘确认弹窗` |
| `Flag_Inverse_` | 反逻辑识别 | `inverse: true`，识别到时**不进入**，未识别到时**进入** | `Flag_Inverse_资源申请领取` |
| `Action_` | 自定义动作 | 调用 Custom Action | `Action_智能策略补充`、`Action_禁用体力检查` |
| `Judge_` | 周期控制 | 通用自定义动作，调用 `JudgeDailyTask` / `JudgeWeeklyTask` | `Judge_专属甜心_Daily` |
| `HitsLimiter_` | 计数限制 | 通用自定义动作，调用 `HitsLimiter` | `HitsLimiter_Click_协理04_黄金` |

**跨任务复用命名**：从 `utils.json` 复制节点到其他文件时，添加后缀（通常为后续节点名称、活动名称）以示区分：

- `Click_事件簿` → `Click_事件簿_进修`（进修副本中）
- `Click_事件簿` → `Click_事件簿_异常`（异常副本中）

**无前缀节点**：模块入口节点直接使用中文描述名，如 `返回主界面`、`领取邮件`、`逸梦`、`体力检查`。

### 2.3 流程控制约定（错题集）

#### next 列表优先级

`next` 列表中的节点顺序是有意义的，按**从上到下**的优先级依次匹配。

你会发现带 `[JumpBack]` 前缀的节点往往位于列表最下面，但这不是硬性规定，你需要根据任务链逻辑自行判断节点顺序。

```json
"next": [
    "Flag_主界面任务",            // 优先级最高：已在主界面，执行"Flag_主界面任务"及其后续节点，不跳回
    "[JumpBack]Click_关闭奖励弹窗", // 第2优先：有弹窗，关闭弹窗后跳回
    "[JumpBack]Click_返回上一级键", // 第3优先：未在根页面，返回上一级后跳回
    "[JumpBack]Click_确定"        // 优先级最低：回收过期资源，点击确定后跳回
]
```

#### 识别 → 操作 → 再识别

尽量减少盲动作节点（无 `recognition` 的 Swipe/Click），保证每一步操作都基于识别。

**推荐**：`识别 A → 点击 A → 识别 B → 点击 B`。**禁止**：`整体识别一次 → 点击 A → 点击 B → 点击 C`。

例如：

界面跳转中，需要 `识别跳转按钮 → 点击跳转按钮 → 识别界面已跳转完成`。你没法保证点完按钮之后画面是否还和之前一样，极端情况下可能点到抽卡里去。

#### 防死循环

盲动作节点（无 `recognition` 的 Swipe/Click）应当使用 `max_hit` 限制最大命中次数，到达上限后框架会自动跳过该节点。

```json
"Flag_进修副本列表最下端": {
    "next": [
        "Click_进入进修副本",
        "Flag_进修副本列表最上端",
        "[JumpBack]Swipe_向上滑动寻找进修副本"
    ]
},
"Swipe_向上滑动寻找进修副本": {
    "action": "Swipe",
    "max_hit": 10,
    "begin": [75, 650, 30, 30],
    "end": [75, 450, 30, 30]
}
```

#### 不要滥用重试

拒绝以下两类重试：

- **容易导致死循环的重试** — 失败后自身再试一次，依旧失败，无限循环直到超时。
- **掩盖失败的重试** — 用重试逃避不稳定的问题，不去真正修复。

例如：

1. 当点击没反应时再点一次 → 通过 `pre_wait_freezes` 等待画面静止，或增加中间节点确认后再执行。
2. 当一个节点出现死循环后加 `max_hit` → 出现死循环一般都是识别问题、逻辑缺陷导致，盲目加 `max_hit` 只会让逻辑中断，出现难以预估的后果。

**推荐**：遇到 bug 时找问题根因，详细到具体哪个节点失败、哪个识别不符合预期，去修补对应节点的识别、操作问题。

#### 减少硬延迟

尽可能少使用长时间的 `pre_delay`、`post_delay`、`timeout`。在等待画面稳定时使用 `pre_wait_freezes` / `post_wait_freezes`。尽可能扩充 `next` 列表，保证任何游戏画面都处于预期中，避免硬延时。

> 设置延迟是在掩盖问题，在用户设备存在卡顿、网络不稳定时仍然会出现问题。

### 2.4 识别策略约定

#### OCR expected 容错

`expected` 应包含常见误识别变体。完整句无法匹配时，可以切分或只取稳定识别的特征字：

```json
"expected": ["每", "母", "每日"]
```

#### OCR expected 正则

`expected` 支持正则表达式：

```json
"expected": ["结束(?!充电)"]
```

上面的例子使用负向前瞻 `(?!充电)` 避免在"你我之间"中误匹配"结束充电了"。

#### 占位符

用户可配置的下拉选项使用 `"by_user_settings"` 占位符，运行时由框架替换为用户选择的值：

```json
"expected": "by_user_settings"
```

#### 模板数组 OR 匹配

`template` 支持数组形式的 OR 匹配，任一模板命中即判定成功：

```json
"template": [
    "好感/手机.png",
    "好感/手机_你我之间夏彦.png",
    "好感/手机_你我之间左然.png",
    "好感/手机_你我之间莫弈.png",
    "好感/手机_你我之间陆景和.png"
]
```

常见场景：同一元素的不同状态（不同角色、亮/暗状态等）。

#### `inverse` 反转识别

当需要判断"某样元素不存在"时才进入流程时使用：

```json
"Flag_Inverse_资源申请领取": {
    "inverse": true,
    "recognition": "OCR",
    "expected": "领取",
    "next": ["返回主界面"]
}
```

> ⚠️ **易错点**：游戏过场动画可能导致截取到中间画面，误触发 inverse 条件。非必要不使用 inverse 。

#### `green_mask` 绿色遮罩

部分图标在不同界面有颜色变化，启用绿色遮罩可以消除颜色干扰，只匹配形状。项目中常用于透明背景导航按钮。

#### ColorMatch 颜色识别

OCR 和 template 识别不适用时，可以尝试颜色匹配（如"战力不足"红色字体提示）：

```json
{
    "recognition": "ColorMatch",
    "roi": [350, 130, 20, 20],
    "lower": [150, 0, 0],
    "upper": [255, 80, 80],
    "count": 10
}
```

### 2.5 `target` 与 `target_offset`

三种点击定位方式：

```json
// 1. 点击匹配区域（默认定位方式）
"target": true

// 2. 点击固定坐标（常用于一键领取奖励）
"target": [550, 1045, 45, 25]

// 3. 相对于 OCR 匹配结果偏移（常用于点文字上方的图片）
"target_offset": [0, -80, 0, 0]
```

### 2.6 日志标记 (focus)

使用 `focus` 字段在日志中输出醒目消息。

```json
"focus": {
    "Node.Recognition.Succeeded": "<span style=\"color:Limegreen\">已完成复盘1次</span>"
}
```

`"Node.Recognition.Succeeded"` 是节点识别成功时发送的消息类型（更多类型见 [回调协议](https://github.com/MaaXYZ/MaaFramework/blob/main/docs/zh_cn/2.3-%E5%9B%9E%E8%B0%83%E5%8D%8F%E8%AE%AE.md)）

**日志颜色**：

| 颜色 | 色值 | 用途 | 举例 |
| --- | --- | --- | --- |
| Limegreen | `#32cd32` | 任务/步骤完成 | 已完成复盘1次 |
| Red | `#FF0000` | 任务出错 | 任务出错，已停止 |
| Dimgray | `#696969` | 普通信息提示 | 选中日常委托 |
| Deepskyblue | `#00BFFF` | （任务完成以外的）积极类提示 | 好感度等级提升 |
| Orange | `#FFA500` | （任务出错以外的）消极类提示 | 该副本今日未开启 |

## Python Agent 编码规范

请先查阅 MaaFramework [Custom & Agent 文档](https://github.com/MaaXYZ/MaaFramework/blob/main/docs/zh_cn/1.3-Custom%26Agent.md#agent)。

### 3.1 路径约定

使用 `pathlib.Path` 构建项目内路径：

```python
from pathlib import Path

CURRENT_FILE_PATH = Path(__file__).resolve()
# agent/custom/action/periodic_task.py → 项目根目录
CONFIG_PATH = (
    CURRENT_FILE_PATH.parent.parent.parent.parent / "config" / "maatot_data.json"
)
```

- `config/maatot_data.json` — Agent 运行时数据（周期任务时间戳等），由 Agent 自动创建。

### 3.2 模块组织

```
agent/
├── main.py              # 入口：venv管理、AgentServer启动
├── custom/
│   ├── __init__.py      # 聚合导入 action + recognition
│   ├── action/
│   │   ├── __init__.py  # 显式声明
│   │   ├── hits_limiter.py
│   │   ├── smart_replenish.py
│   │   ├── dynamic_override.py
│   │   └── periodic_task.py
│   └── recognition/
│       ├── __init__.py
│       └── ap_check.py
└── utils/
    ├── __init__.py
    ├── logger.py        # 日志配置
    ├── params.py        # 参数解析工具
    ├── json_io.py       # JSON 读写工具
    └── time.py          # 时间差格式化
```

- 子模块通过 `__init__.py` 聚合导入
- action 的 `__all__` 显式声明所有注册类名

> 新增 Custom Action/Recognition 时同步更新 `__init__.py`
